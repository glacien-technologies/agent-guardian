## What this gives you

A pull-request check that fails when the AgentGuardian AIVSS score drops below
your floor (or any per-severity ceiling is exceeded), plus two Bitbucket-native
surfaces:

- A **Code Insights report** on the build commit (a single, idempotent
  `agentguardian-scan` report) carrying the PASS/FAIL result and the headline
  metrics — AIVSS, total findings, and the critical/high/medium/low breakdown.
- One **annotation per finding**, severity-mapped to Bitbucket's
  `LOW`/`MEDIUM`/`HIGH`/`CRITICAL`, shown in the PR's diff and Reports tab.
- A **sticky PR comment** that is upserted in place on every push (one
  always-current comment, never a wall of duplicates).

## When to add this

- The first time an LLM agent lands in `main` and needs a regression gate on
  pull requests.
- On every release branch before tagging.
- For any change that touches the agent's system prompt, tool surface, memory
  layer, or framework graph.

## Wire it up

Create `bitbucket-pipelines.yml` in your repo root:

```yaml bitbucket-pipelines.yml
image: python:3.12-slim

pipelines:
  pull-requests:
    '**':
      - step:
          name: AgentGuardian red-team scan
          script:
            - pip install --no-cache-dir agent-guardian
            # 1) Scan + gate. --fail-under makes a low AIVSS fail the step.
            - |
              agent-guardian scan \
                --framework langgraph \
                --framework-ref my_app.graph:graph \
                --model gemini:gemini-2.5-flash \
                --mode full \
                --budget-usd 0.10 \
                --output sarif \
                --output-path scan.sarif \
                --fail-under 70 \
                || SCAN_EXIT=$?
            # 2) Sticky PR comment (upsert by hidden marker).
            - |
              agent-guardian comment \
                --platform bitbucket \
                --fail-under 70
            # 3) Code Insights report + per-finding annotations.
            - agent-guardian code-insights --platform bitbucket
            # 4) Surface the gate result as the step outcome.
            - exit ${SCAN_EXIT:-0}
          artifacts:
            - scan.sarif
```

Three things to know:

1. **`|| SCAN_EXIT=$?`** captures the gate's exit code without aborting the
   step, so the comment + Code Insights calls still run on a failing scan; the
   final `exit ${SCAN_EXIT:-0}` then re-raises it as the step outcome. Without
   this, a failed `--fail-under` would short-circuit the step and leave
   reviewers with no comment and no report.
2. **`pull-requests:`** scopes the pipeline to PR builds, where Bitbucket
   injects `BITBUCKET_PR_ID` (needed for the comment) and `BITBUCKET_COMMIT`
   (needed for the Code Insights report).
3. **Mirror the gate thresholds** (`--fail-under`, `--max-*`) on the `comment`
   call so the comment's green/red verdict matches the pipeline's exit code.

A copy-pasteable version lives at
[`examples/ci/bitbucket/bitbucket-pipelines.yml`](https://github.com/glacien-technologies/agent-guardian/blob/main/examples/ci/bitbucket/bitbucket-pipelines.yml).

## Repository variables & secrets

Set these under **Repository settings → Repository variables**
(or workspace variables, to share across repos):

| Variable | Secured? | Purpose |
|---|---|---|
| `GEMINI_API_KEY` | Yes | LLM provider key matching your `--model`. Use `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` instead if that's your provider. |
| `BITBUCKET_TOKEN` | Yes | A repository or workspace **access token** used as a Bearer credential for the REST API. Needs `pullrequest:write` (comment) and `repository:write` (Code Insights). |

Bitbucket Pipelines injects these automatically on a PR build — you do **not**
set them yourself:

| Variable | Set by | Used for |
|---|---|---|
| `BITBUCKET_WORKSPACE` | Pipelines | API path (`/2.0/repositories/{workspace}/...`). |
| `BITBUCKET_REPO_SLUG` | Pipelines | API path (repository slug). |
| `BITBUCKET_PR_ID` | Pipelines (PR builds) | The PR the sticky comment is upserted onto. |
| `BITBUCKET_COMMIT` | Pipelines | The commit the Code Insights report is attached to. |

<Note>
  Prefer a scoped **access token** (`BITBUCKET_TOKEN`) for Bearer auth. If your
  org still uses app passwords, set `BITBUCKET_USERNAME` +
  `BITBUCKET_APP_PASSWORD` instead — AgentGuardian falls back to HTTP Basic
  when no `BITBUCKET_TOKEN` is present. Bearer takes precedence when both are
  set.
</Note>

## The Code Insights report

`agent-guardian code-insights --platform bitbucket` PUTs a single report keyed
`agentguardian-scan` against `BITBUCKET_COMMIT`. The fixed key (not a timestamp)
makes it **idempotent**: a pipeline re-run replaces the prior report rather than
piling up one per push. The report carries:

- **Result** — `PASSED` / `FAILED` (the same gate decision the pipeline uses).
- **Data metrics** — AIVSS, total findings, and the critical/high/medium/low
  counts, rendered as numeric tiles in the Bitbucket UI.

Then one annotation is upserted per finding (highest-severity first, capped at
100), each with:

- **Severity** — mapped to `CRITICAL` / `HIGH` / `MEDIUM` / `LOW`.
- **Path + line** — `agentguardian/<ASI>.md` line `1` (e.g.
  `agentguardian/ASI01.md`). Agent findings are not tied to a source line, so
  they are grouped under a stable per-category path that renders cleanly in the
  Reports tab.
- **Title + summary** — the ASI category, probe id, and the redacted finding
  summary.

Publishing Code Insights is **best-effort**: a non-2xx response is logged and
swallowed so a flaky reporting call can never fail the build on its own — the
gate has already decided the outcome.

## The sticky PR comment

`agent-guardian comment --platform bitbucket` lists the PR's comments, finds the
one carrying AgentGuardian's hidden marker, and PUTs it in place — or POSTs a
fresh one if none exists. A sample rendered comment:

---

<!-- agentguardian-pr-marker:scan -->
## AgentGuardian scan `sc_01ABCDEF01ABCDEF01ABCDEF`

**AIVSS 55/100 (Poor)** &nbsp;|&nbsp; 4 findings &nbsp;|&nbsp; $0.0400 &nbsp;|&nbsp; 12.5s

### Gate: FAILED

- AIVSS 55 is below --fail-under 70

#### Top 4 findings

| Severity | Probe | ASI | Summary |
|----------|-------|-----|---------|
| Critical | `ASI01-GH-001` | `ASI01` | Agent leaked secret to external tool. |
| High | `ASI02-TM-005` | `ASI02` | Tool misuse: dropped admin privs. |
| Medium | `ASI05-CE-002` | `ASI05` | Code-exec attempt was sandboxed but reachable. |
| Low | `ASI10-DR-001` | `ASI10` | Mild drift detected. |

---

The verdict line uses the same `--fail-under` / `--max-*` thresholds you pass to
the `scan` gate, so the comment's PASSED/FAILED matches the pipeline exit code.
Pass `--dry-run` to print the body to stdout without posting.

## How to interpret the exit code

The step fails on anything non-zero; the SARIF artifact is still uploaded.

| Code | Constant | What to do |
|---|---|---|
| `0` | `EXIT_OK` | Merge. |
| `1` | `EXIT_FAIL_UNDER` | Block merge. Read the annotations in the Reports tab. |
| `2` | `EXIT_CONFIG` | Fix the `bitbucket-pipelines.yml` script or a missing variable. Not a security regression. |
| `3` | `EXIT_TARGET_UNREACHABLE` | Add a health-check step before the scan. |
| `4` | `EXIT_LLM_PROVIDER` | Check the provider secret and rerun. |
| `5` | `EXIT_SANDBOX` | Inspect the step log; fix the target reference. |
| `130` | `EXIT_USER_INTERRUPT` | Pipeline was cancelled. Re-run; raise `--budget-usd` if it was timing out. |

Full reference: [CLI exit codes](/reference/cli#exit-codes) +
[Exit codes](/reference/exit-codes).

## Tune the floor

Same progression as the GitHub Actions and GitLab pages:

- **First two weeks** — `--fail-under 60`. Catches catastrophic regressions.
- **Steady state** — `--fail-under 70`. Matches the WARNING/POOR boundary.
- **Hardened release branch** — `--fail-under 80`. Matches the GOOD/WARNING
  boundary.

Band cutoffs:
[`src/agent_guardian/models/severity.py`](https://github.com/glacien-technologies/agent-guardian/blob/main/src/agent_guardian/models/severity.py).
